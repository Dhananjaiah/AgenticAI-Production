0. Start from any supported Ubuntu host

Use Ubuntu on a local computer, local VM, cloud instance, WSL, or another supported host. The course commands are identical.

Required: Ubuntu Bash, Python 3.11+, Git, an editor, and network access for live provider calls. Host provisioning is outside the lesson; start once you have an Ubuntu terminal.
Pass: your Ubuntu prompt is available and you can create files in your Linux home directory.

1. Verify the Ubuntu tools

Open Ubuntu. These are the canonical course commands.

UBUNTU TERMINAL
python3 --version
git --version
code --version

What this doesChecks Python and Git from Ubuntu; the editor connection is host-specific.

Why we do itThe course requires Python 3.11+. If VS Code is connected to this host, code opens the folder. Otherwise use the editor connection appropriate to the host.

Pass: Python prints 3.11+ and Git prints a version. Use VS Code or another editor connection appropriate to this Ubuntu host.

2. Put the repository in the Linux home folder

Keep course code under ~/src. Keep the course project in your Ubuntu home directory.

CLONE OR REUSE THE COURSE REPOSITORY
mkdir -p ~/src
if [ ! -d ~/src/agentic-ai-40days/.git ]; then
  git clone https://github.com/Dhananjaiah/Agentic-AI-40Days.git ~/src/agentic-ai-40days
fi
cd ~/src/agentic-ai-40days
pwd
test -f requirements.txt && echo "requirements.txt found"
test -f pyproject.toml && echo "pyproject.toml found"
test -f .env.example && echo ".env.example found"
code .

What this doesCreates a Linux workspace, clones the course on the first run, verifies the required files, and opens the Ubuntu folder in VS Code when that command is available.

Why we do itKeeping the repository in the Ubuntu home directory keeps Git, Python, permissions, containers, and later deployment tooling consistent.

Pass: pwd starts with /home/ and all three files are found. Open the folder in your available editor.

3. Create the project environment

Run all remaining Day 0 commands from ~/src/agentic-ai-40days in Ubuntu.

CREATE AND ACTIVATE .VENV
python3 -m venv .venv
source .venv/bin/activate
python --version
python -c "import sys; print(sys.executable)"

What this doesCreates an isolated Python environment, activates it, and shows the active interpreter.

Why we do itEach course project keeps its own dependencies. Activation prevents package conflicts.

Pass: the prompt begins with (.venv), and the executable ends in /.venv/bin/python.

4. Install the pinned course packages

Keep (.venv) visible before installing anything.

INSTALL DEPENDENCIES AND COURSE HELPER
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install -e .

What this doesUpdates pip inside the active environment, installs pinned packages, and installs the local course helper in editable mode.

Why we do itThe labs import provider SDKs and shared.llm. Editable installation makes the helper importable from every lab folder.

Pass: every command completes without an error and python -c "import shared.llm" succeeds.

5. Create private local configuration

Stop screen capture before adding a real API key. Never paste a key into a terminal, source file, recording, screenshot, chat, or Git commit.

CREATE LOCAL .ENV
cp .env.example .env
code .env

What this doesCopies the safe template into a private local file and opens it in VS Code.

Why we do itThe template documents variable names. The real credential belongs only in ignored local .env.

Private action: replace only the selected provider placeholder while recording is stopped. Save and close .env before resuming.
PROVE GIT IGNORES THE SECRET
git check-ignore -v .env

What this doesAsks Git which ignore rule prevents .env from being tracked.

Why we do itAn API key can create usage and cost. We need visible proof that Git will not add this secret file by accident.

Pass: Git prints the matching ignore rule and the .env path. Stop if it prints nothing.

VERIFY LOCAL SETUP

7. Run the first real AI call

This contacts the configured provider, sends a harmless prompt outside your machine, and may create usage charges.

RUN HELLO AI
python phase-0-get-ready/day-00/labs/lab-0.5c-hello-ai/solution/hello_ai.py

What this doesLoads local configuration, sends a small prompt, and prints response text plus usage information.

Why we do itThis is the end-to-end proof: Ubuntu Python, packages, private configuration, network, provider authentication, and model response worked together.

Pass: meaningful generated text and usage appear. Exact wording and token counts vary.
CHANGE ONE PROMPT, THEN RERUN
code phase-0-get-ready/day-00/labs/lab-0.5c-hello-ai/solution/hello_ai.py
python phase-0-get-ready/day-00/labs/lab-0.5c-hello-ai/solution/hello_ai.py

What this doesOpens the example, lets you change only its prompt, then runs it again.

Why we do itA controlled change shows how instructions affect output without promising identical wording.

Suggested harmless prompt: Explain an API key to a ten-year-old in two sentences.

8. Troubleshoot by layer

Read the first useful error, name the failing layer, change one thing, then rerun the same check.

LOCAL ENVIRONMENT CHECKS
python --version
python -c "import sys; print(sys.executable)"
python -m pip --version
python phase-0-get-ready/day-00/labs/lab-0.5b-setup-project/solution/check_setup.py

What this doesRechecks Python, the active environment, pip, packages, imports, and key presence in order.

Why we do itThis identifies whether a problem is Ubuntu setup, the virtual environment, packages, configuration, network, or provider access.

REINSTALL IF AN IMPORT IS MISSING
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip install -e .

What this doesReactivates the environment and reinstalls dependencies and the local package.

Why we do itUse this only when an error identifies a missing module or missing shared package.

If python3 -m venv fails, run sudo apt update && sudo apt install -y python3-venv, then rerun the same command.
Finish or leave the environment
DEACTIVATE
deactivate

What this doesLeaves the virtual environment in the current Ubuntu terminal.

Why we do itThis is optional. Keep .venv and .env because later days use them.

Day 0 proves one controlled request path in Ubuntu. It does not yet prove production readiness, stable output, fixed cost, or safe handling of sensitive production data.
