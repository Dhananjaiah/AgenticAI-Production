1. Verify the required tools

WINDOWS POWERSHELL
python --version
git --version
code --version

What this doesAsks Python, Git, and VS Code to print their installed versions.

Why we do itIf the terminal cannot find a tool, the later commands will fail. Fixing that first keeps the rest of the setup clear.

Pass: Python reports version 3.11 or newer, and Git and VS Code return version information.

2. Open the course repository

GO TO THE PROJECT
Set-Location "C:\Users\DhananjaiahMaroju\Downloads\ALL\Agentic-AI-40Days"
code .
Get-Location
Test-Path requirements.txt
Test-Path pyproject.toml
Test-Path .env.example

What this doesMoves into the repository, opens it in VS Code, prints the current folder, and checks three required files.

Why we do itPython and pip commands depend on the working directory. The three True results prove we are at the repository root.

Pass: all three Test-Path commands return True.

3. Create and activate the virtual environment

CREATE .VENV
python -m venv .venv
.\.venv\Scripts\Activate.ps1

What this doesCreates a private Python environment in .venv and activates it in the current terminal.

Why we do itThe project receives its own packages without changing the global Python installation or another project's dependencies.

PROVE WHICH PYTHON IS ACTIVE
python -c "import sys; print(sys.executable)"
python -m pip --version

What this doesPrints the exact Python executable and pip location used by this terminal.

Why we do itThe paths should point inside .venv. That is stronger evidence than relying only on the terminal prompt.

Pass: both paths include .venv.

4. Install the course packages

INSTALL DEPENDENCIES
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python -m pip install -e .

What this doesUpdates pip, installs the shared dependencies, and installs this repository as an editable Python package.

Why we do itThe lab imports provider libraries and shared course helpers. Editable installation makes those local helpers importable while we continue changing the code.

5. Create the private local configuration

Stop or hide screen capture before adding a real API key. Never paste the key into the terminal, source code, recording, screenshot, chat, or Git.
CREATE LOCAL .ENV
Copy-Item .env.example .env
code .env

What this doesCopies the safe configuration template into a local .env file and opens it for editing.

Why we do itThe template shows the required names. The local file holds the real private value and must stay outside Git.

Privately replace only the selected provider's placeholder value. Save and close .env, then resume recording. Do not show the file again.
PROVE GIT IGNORES THE SECRET
git check-ignore -v .env

What this doesAsks Git which ignore rule prevents .env from being tracked.

Why we do itA real API key can allow usage and cost. We need proof that Git will not add this secret file by accident.

Pass: Git prints the matching ignore rule and .env path. Stop if it prints nothing.

6. Run the no-cost setup checker

VERIFY LOCAL SETUP
python phase-0-get-ready/day-00/labs/lab-0.5b-setup-project/solution/check_setup.py

What this doesChecks the Python version, virtual environment, required packages, shared imports, and presence of the configured API key.

Why we do itThis separates local setup problems from provider or network problems before we spend money on a model request.

Pass: the script reports that all checks passed. This does not yet prove the key is accepted by the provider.

7. Run the first real AI call

This step contacts the configured provider, sends the prompt outside your machine, and may create usage charges. Use only harmless text.
RUN HELLO AI
python phase-0-get-ready/day-00/labs/lab-0.5c-hello-ai/solution/hello_ai.py

What this doesLoads the local configuration, sends a small prompt to the selected AI provider, and prints the generated response and usage information.

Why we do itThis is the end-to-end proof: local Python, installed packages, private configuration, network access, provider authentication, and model response all worked together.

Pass: the command finishes with meaningful generated text and usage information. The exact wording and token count can change.

9. Troubleshoot by layer

LOCAL ENVIRONMENT CHECKS
python --version
python -c "import sys; print(sys.executable)"
python -m pip --version
python phase-0-get-ready/day-00/labs/lab-0.5b-setup-project/solution/check_setup.py

What this doesRechecks Python, the active environment, pip, packages, imports, and key presence in a useful order.

Why we do itRead the first useful error, name the failing layer, change one thing, and rerun the same failed command.

REINSTALL IF AN IMPORT IS MISSING
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pip install -e .

What this doesReactivates the virtual environment and reinstalls the dependencies and local package.

Why we do itUse this only when the error says a required module or the shared package is missing.

For authentication errors, check or replace the key privately in the provider console. Never print the key to diagnose it.
macOS or Linux command differences

source .venv/bin/activate

What this doesCreates and activates the same virtual environment using Unix-style paths.

Why we do itThe goal is identical; only the executable name and activation path differ.

CREATE LOCAL CONFIGURATION
cp .env.example .env
code .env

What this doesCopies the template using the macOS/Linux command and opens the private file.

Why we do itThe API key still belongs only in local .env, regardless of operating system.

Finish or leave the environment
DEACTIVATE
deactivate

What this doesLeaves the virtual environment in the current terminal.

Why we do itThis is optional. Keep .venv and .env because later course days use them.
