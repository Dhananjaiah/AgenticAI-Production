Real work problem

Software cannot reliably sort a changing paragraph.

One answer

A person can read a friendly paragraph.

Hundreds of reviews

A team needs consistent fields it can count, filter, and route.

One friendly paragraph may be useful to a person. It is difficult for software to count, sort, filter, or route. A support team with hundreds of reviews needs consistent fields. Each review should have a sentiment, a topic, and a short summary.
Mental model

Conversation versus a filled-in form.

Chatty

Shape can move.

Structured

Chatty text can change shape from one answer to the next. A structured record uses the same labels every time. That predictable shape lets normal code read one field without guessing where it appears in a paragraph.

Role says who the assistant is. Task says what it must do. Rules set boundaries. Unsure tells it not to guess. Format defines the response shape. Short, precise instructions are enough. We improve them when real output shows a gap.
Structured output

JSON is a filled-in form for software.

One record: { }

{"sentiment":"positive", "topic":"delivery", "summary":"Arrived early"}

List: [ ]

[ {"sentiment":"positive", ...}, {"sentiment":"negative", ...} ]
JSON is text written as labelled values that software can read. Curly braces hold one record. Square brackets hold a list of records. In our sorter, each record has sentiment, topic, and summary. The labels must match what our code expects.
Parsing

Parsing can fail. Parsed data can still have the wrong fields.
The provider returns text, even when that text contains JSON. Parsing turns the JSON text into a Python list or dictionary. Our helper also removes common JSON code fences. Parsing can still fail when the text is malformed, so parsing is not the final safety check.
Two different checks

Valid JSON is not automatically valid business data.

Parse check

Can the text become data?

Schema check

Are required fields and allowed values present?

Meaning still needs evaluation after shape checks pass.
Valid JSON only proves that the punctuation can be parsed. It does not prove required fields exist or that sentiment uses an approved value. We need schema validation after parsing. We also need human or business checks when the meaning matters.
Schema

Describe exactly what we accept.

class Review(BaseModel): sentiment: Literal[ "positive", "negative", "neutral", "unclear" ] topic: str summary: str
The Pydantic Review model describes valid data. Sentiment can only be positive, negative, neutral, or unclear. Topic and summary must be strings. If a field is missing or an allowed value is broken, validation raises a clear error before the program trusts the result.

Failure: bounded retry → flagged fallback.
The order matters: request, parse, validate, and only then use the result. If parsing or validation fails, retry within a small limit. If every attempt fails, return a safe fallback marked for human review.

Bounded retry

Try again, but know when to stop.

Attempt 1
→
Attempt 2
→
Attempt 3
→
Fallback
A retry gives a temporary or variable failure another chance. It is not an endless loop. Our maximum is three attempts. Each attempt may create cost and delay, so production code also needs timeout, backoff, and rate-limit handling.
Safe fallback

Do not disguise failure as success.

Review( sentiment="unclear", topic="needs-review", summary="Could not classify automatically" )
After all attempts fail, the program returns sentiment unclear, topic needs-review, and a summary saying automatic classification failed. The fallback does not pretend the classification succeeded. It keeps the program running and sends the item toward human review.
Deterministic failure

Force known bad data.

Bad value

{"sentiment":"ecstatic", "topic":"x", "summary":"y"}

Missing field

{"sentiment":"positive", "topic":"x"}
We do not wait for the model to fail during a recording. We directly give the validator an unsupported sentiment and a record with a missing field. This test is deterministic. It proves the schema rejects those known bad examples without making a provider call.
Production boundary

Shape checks are necessary, not sufficient.

Validity

Fields and allowed values.

Meaning

Is the classification actually right?

Operations

Timeout, backoff, queue, owner, alert.

Validation proves the output has the declared shape and allowed values. It does not prove the sentiment is factually or semantically correct. Retries can increase cost and repeat a bad request. Fallback needs an owner, a queue, and monitoring in a real system.
